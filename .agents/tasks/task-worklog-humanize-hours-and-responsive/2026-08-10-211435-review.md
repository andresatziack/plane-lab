## High-level view

The user's question — "are you sure the frontend changed?" — has a yes and a but. Thirteen files under `apps/web` changed across the two rounds, and this pass rewrote five of them again; none of it, nor the `preview` commit that first introduced `format_hours_human`, exists on the remote. Pushing `preview`, pushing the branch and dispatching `build-branch.yml` by hand is the whole gate, and no screenshot means anything until then.

The responsive half changed tool. Viewport breakpoints were the wrong instrument inside a peek that is `md:w-[50%]` of that same viewport, so the section now declares `@container` and asks about its own width. I checked that the new utilities actually compile and are actually scanned, because a container-query class that fails either step degrades silently to the phone layout with nothing red anywhere. The consequence to accept knowingly is that desktop is no longer pixel-identical: between 1024 and 1279 the side peek shows a 2×2 totals grid and stacked work log entries where it showed four columns and one row.

The hour rule is now enforced by two guards. The AST scan is the right shape — it reads names, not prose, and it proves it can fail — but it watches `plane/app` and `plane/utils` for the identifier `format_hours`, which is narrower than the rule it defends: a decimal hour assembled with an f-string, or built anywhere else in the tree, walks past it. The twin walker is asserted on five payloads and not on the four with the worst history, `/preview` among them.

Both written answers stand. Keeping `hours_display` on the origins bucket means the new invariant needs no exception on its first application, which is a better trade than dropping the field, and D68 no longer claims a defect that surface never had; correcting the `flex-wrap` comments rather than adding `sm:flex-nowrap` avoids restoring the overflow the breakpoint would have brought back.

## Container queries, verified rather than reasoned about

Compiling the nineteen new or changed utilities through the repo's own `tailwindcss@4.1.17` emits `container-type: inline-size` for `.@container`, `@container (width >= 24rem)` for `@sm`, `28rem` for `@md`, `36rem` for `@xl`, and ordinary media queries for `md:order-none`, `md:border-b-0` and `md:!w-[400px]` — the last still `width: 400px !important`, which is what keeps the desktop rail from reverting to full width. Running the oxide scanner over `apps/web/core/components` extracts `@container`, `@sm:grid-cols-3`, `@md:grid-cols-3`, `@md:text-base`, `@xl:grid-cols-4`, `@xl:grid-cols-3` and the four `@xl:` flex utilities, including both literals of the `cards.length === 4` ternary.

Two mechanics the fix rests on: container size features resolve against the container's content box, so `@container` on the allowance indicator measures the 334px inside its `px-3` at a 390px phone rather than the 358px box; and `@plane/ui`'s `Tooltip` defaults to `renderByDefault`, taking the `cloneElement` path, so the `min-w-0` card is the grid item — its other branch wraps children in a `div` and would have defeated the fix silently.

Where the container queries change desktop, the numbers are:

```
side peek     peek width   container (px-8)   totals grid      previously
 390px         390          358 (px-4)         2 cols           2 cols (md not met)
 768           384          320                2 cols           4 cols  <- the v1 defect
1024           512          448                2 cols           4 cols
1280           640          576                4 cols (exactly) 4 cols
1280 Firefox   640          ~564               2 cols           4 cols
1920           960          896                4 cols           4 cols
```

The 768px row is the inversion the first pass flagged, now gone. The 1024 row is a real change in desktop appearance: a 2×2 grid and stacked entry rows where the branch's own acceptance criterion promised byte-identical geometry. It fits better — four columns at a 448px container leave 82px of card interior against a `1h 52min 30s` value that needs ~96px — but it is a visible change, and D69 records the arithmetic without saying so in those words.

The 1280 rows are the fragile part. `@xl` is met exactly, with nothing to spare, and the peek's scroll container is `.vertical-scrollbar`; the fork's own stylesheet hides webkit scrollbars but restores `scrollbar-width: initial` under `@-moz-document`, so Firefox spends ~12px of that container and drops to two columns at the same window size where Chrome shows four. The full work item page is in the same neighbourhood: a 1280px window with the app sidebar and a `min-w-96` properties rail leaves roughly 574px inside `px-9`, two pixels under the threshold. `@lg` (512px) would clear both with ~98px of card interior, which still fits the longest three-term duration.

## What the guards catch, and what walks past

The AST scan pins its allow-list to two paths, asserts the export schema still binds the decimal renderer so the exception shrinks if the export ever moves, and feeds itself an import, a bare call, an attribute call, a docstring, a comment and `format_hours_human` to prove it can both fire and stay quiet.

Its reach is narrower than the rule it defends, in two ways that hold today and are each one commit from not holding. `SCREEN_PAYLOAD_ROOTS` is `("plane/app", "plane/utils")`, and the match is on one identifier, so a decimal hour assembled inline passes: `bgtasks/issue_activities_task.py::_service_log_batch_summary` builds `f"{total_logged} h"` — `"1.5000 h"` — for the work log activity row today, and the guard reports a clean tree. That string is invisible only by accident: the web activity list switches on `activity.field` and `"service_log"` falls through to `default: return null`, so the row renders nothing at all. The day someone renders it, D68 is broken again and the guard is silent.

The twin walker has the opposite shape of problem: correct, and opt-in. Five payloads assert `hour_fields_missing_a_rendered_twin(...) == []` — both overage previews, the billing consolidation, and both alert panel entries. The four that do not are `/preview` totals in `views/service_log/base.py`, `issue_client_totals`, the allowance ledger in `allowance_credits` and `contract_balance_statement`, which is close to the list of payloads that caused the previous four rounds; `/preview` is the one that shipped no twins at all. Each already has a test that builds the payload, so the assertion is one line each.

R11 is untouched by the four fields added to the alert entries: both panels are Admin surfaces reached through the `service_reports` and `service_contract` views, the raw hours were already in those payloads, and no client-facing payload gained a field in this commit.

## Verification, re-run

`run-api-tests.sh -q` with no marker and no path filter: 2611 passed in 560s, so the three consolidation failures are gone and nothing new appeared. Every file under `plane/tests/{unit,contract}` now carries a `unit` or `contract` marker, so the filtered run and the conventions-prescribed run can no longer disagree about which files exist. `ruff check apps/api` is 16 errors, all pre-existing and none in a touched file. `REBUILD=1 run-web-checks.sh types` exits clean and oxlint reports 0 warnings and 0 errors over the 15 touched web files.

The new payload assertions are exact strings with a non-whole-minute case each — `15h 15min` for the allowance overage, `1h 43min 20s` for the hours-per-issue average, `-3h` and `-15h` on the alert entries — and the two absence assertions carry their reason in the message: no `amount` on a registration pendency because `R$ 0,00` would make a missing price sheet look like a finished calculation, and no average at all on an empty selection because a rendered `0min` would be an answer where there is none.

Not tested, and unchanged from the first pass: anything on the web side. This fork has no JS test runner, so the container-query conversion is guarded by class-string reasoning, the Tailwind compile check above and nothing else. A manual matrix at 390 / 768 / 1024 / 1280 / 1440px across side-peek, modal and full-screen, in Chrome and Firefox, against a real build is still the only verification that can see a breakpoint — and 1280 in Firefox is now a specific cell to look at.
