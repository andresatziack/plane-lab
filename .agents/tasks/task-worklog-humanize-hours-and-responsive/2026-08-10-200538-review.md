# Clock-duration rendering for every hour on screen, plus mobile-first prefixing in the work log UI

Two independent changes on one branch. The API half makes `format_hours_human` the single renderer for every user-facing hour, teaches it to emit a seconds term when a value is not whole-minute aligned (`1.875h -> "1h 52min 30s"` instead of falling back to `"1,875h"`), and adds the `_display` twins that were missing from `/preview`, the overage previews, the alert panel, the billing consolidation and the hours-per-issue average. The web half adds Tailwind breakpoint prefixes across `service-logs/*` and the peek shell so a 390px screen gets two-column cards, wrapping button rows and stacked form pairs, with the classes from `md`/`sm` up intended to be the ones that were unconditional before. D68 records the hour decision; `format_hours` survives only in the CSV/XLSX exporter.

**Watch for:** the reported `32,25h` on the phone is not a code defect — **confirmed** that neither this branch nor the earlier humanization work exists on the remote (`origin` has no `fix/worklog-horas-legiveis-e-responsivo`, and local `preview` is 5 commits ahead of `origin/preview`, including `d5bd45b9f`, the commit that introduced `format_hours_human`), so the phone is running a build that predates both rounds. **Confirmed**: three tests in `plane/tests/unit/utils/test_service_billing.py` now fail because of the new `hours_display` keys, and the marker-filtered verification run could not see them. **Confirmed**: the responsive prefixes key off viewport width while the peek is `md:w-[50%]` of that viewport, so from 768px the totals grid returns to four columns inside a 320px container — a narrower card than the 390px phone case this change set out to fix.

**Verdict**: NEEDS_CHANGES

## High-level view

The user's phone is not showing this code. The work branch was never pushed, and neither were the five `preview` commits it is built on, so the deployed environment has neither the earlier `format_hours_human` work nor this one. Verifying "does the Peek still say 32,25h" has to wait for a push plus a `build-branch` dispatch, because that workflow is `workflow_dispatch` only.

On the API side the consolidation is complete — `format_hours` has three non-test callers left, all in the export schema — but nothing enforces it. This is the fourth pass at the same class of defect, and the rule that every hour field ships a rendered twin still lives only in comments and reviewer attention.

Six payloads gained new `_display` fields, declared as required in `packages/types`. The billing consolidation is reached through `as unknown as` casts in `billing-tab.tsx`, so TypeScript cannot verify those field names; the only thing that checked that payload's shape was a set of exact-dict assertions in `test_service_billing.py`, and those three assertions now fail. They were invisible to the `-m "unit or contract"` run because that file carries no marker — one of four unmarked files out of 95, and the fork's conventions document prescribes running the suite without a marker filter.

The responsive work is additive and reads carefully, but it treats viewport width as a proxy for container width. Inside a side peek that is full width below `md` and half the viewport above it, the `md:` and `sm:` reverts fire exactly when the container halves, so the 768–1500px band gets less room per card than the phone layout it replaced. The repo already uses `@container` elsewhere, which is the tool that matches this geometry.

Two smaller gaps: in full-screen peek mode below `md` the properties rail now stacks after the entire content column, putting state, assignees and dates below the description and the activity feed; and several comments claim a row "never wraps from `sm` up" when the `flex-wrap` they add has no breakpoint variant.

## Nothing enforces the single-renderer rule

`grep -rn "format_hours(" apps/api/plane` outside tests returns the definition plus the three export-schema calls, so the migration itself is complete (confirmed). What is not durable is the boundary: the export exception is a code comment, and the "every hour field ships a `_display` twin" contract is enforced by nobody. This branch is the fourth pass at the same defect — `/preview` shipped no twins at all, the alert panel printed `-2.0000`, the billing screen concatenated a literal `h` onto `1.2500`, and the form printed `1.2500`. A test that fails when a serializer, view, portal, allowance, pool, reports or billing module imports `format_hours`, or one that asserts every `*_hours` key in a screen payload has a `*_hours_display` sibling, turns the fifth omission into a red test instead of another user report.

## The breakpoints describe the viewport; the peek describes half of it

`peekOverviewIssueClassName` gives the side peek `w-full ... md:w-[50%]`, and the content wrapper is now `px-4 md:px-8`. So `md` is simultaneously where the padding doubles, where the totals grid returns to four columns, and where the container halves:

```
viewport  peek width   inner (px-8)   4 cards, gap-2   card interior (px-3)
 390       390          358 (px-4)     2 cards -> 175          151   <- the fixed case
 768       384          320            74                       50   <- worse than the bug
1024       512          448           106                       82
1280       640          576           138                      114
1920       960          896           218                      194
```

Below roughly 1576px of viewport, the four-column desktop layout leaves each card less interior than the two-column phone layout does at 390px (confirmed by the class strings and Tailwind's default breakpoints; no browser available to screenshot it). `Horas equivalentes` alone exceeds 50px at `text-xs`, and `1h 52min 30s` at `md:text-base` needs roughly twice that. `break-words` keeps the text inside the border, so the failure mode is a card wrapped into four or five lines rather than text escaping the box — the same defect, less loudly. Full-screen mode has the same shape: at a 768px viewport the `md:!w-[400px]` rail leaves 336px of inner content, so the four-column grid gets 54px per card.

The same inversion applies to every `sm:` revert inside the peek. `service-log-list-item.tsx` returns to a single row with up to four badges and two icon buttons at 640px, and `service-allowance-indicator.tsx` returns to three columns there; from 768px up those rows live in a container half the width of the viewport that triggered them.

`@container` with `@md:`-style variants matches this geometry and is already used in the repo (`settings/content-wrapper.tsx`, `settings/profile/modal.tsx`). Failing that, gating the work-log grid at `xl` instead of `md` would at least stop the mid-range band from being the worst case. `service-log-form.tsx` and `service-log-modal.tsx` are the one place the current approach is right: `ModalCore` is portalled and sized against the viewport, so `sm:` there means what it says.

## Full-screen peek on a phone puts properties last

The outer row became `flex w-full flex-col overflow-auto md:h-full md:flex-row` and the 400px rail became `w-full ... md:!w-[400px]`, which below `md` stacks the rail _after_ the content column. The reading order on a phone becomes title, description, work log, activity feed, and only then state, assignees, dates and the rest of the properties — several screens of scrolling to reach the controls a technician opens the item for (confirmed). `order-first md:order-none` on the rail, or `flex-col-reverse` with the matching `md:flex-row`, keeps the desktop geometry and puts the properties in reach.

The `!w-[400px]` bang was deliberately preserved and is what lets `md:!w-[400px]` beat the new `w-full` base; dropping it or modernising it to `w-[400px]!` silently reverts the desktop rail to full width, and the code comment saying so should stay.

## `flex-wrap` is unconditional, and the comments say otherwise

`service-log-section.tsx` gets `flex flex-wrap items-center justify-between gap-y-2` with a comment that `flex-wrap` "cannot change a row that already fits, so wide layouts are untouched", and `service-allowance-indicator.tsx` gets `flex flex-wrap ...` with a comment that "from `sm` up the row never wraps, which is the behaviour it had before". Neither adds `sm:flex-nowrap` (confirmed), so both rows wrap at any width once the content stops fitting. That is a better failure mode than the previous overflow, but it is not the "identical from `sm` up" guarantee the comments claim: with four action buttons and a longer translated title, a narrow desktop window now wraps where it used to overflow. Either correct the comment or add the variant. Same category, already flagged by the author: `leading-tight` on the card labels applies at every width.

## New payload fields nobody asserts

`overage_hours_display` (both overage previews), `balance_hours_display` (period and allowance alert entries), `hours_display` (consolidation origins, commercial pendencies, registration pendencies, internal work) and `average_equivalent_hours_per_issue_display` are declared as required properties in `packages/types`, and no test asserts any of them (confirmed). Both producers of each pair are correct on this tree, but a future producer that misses one renders a blank value, or `Saldo: undefined` in the `attention-tab.tsx` template string, with nothing red in between.

The origins bucket is the one field with no consumer at all: `billing-tab.tsx` renders `origins.*.amount_display` in that table and never the hours, so `hours_display` on origins is unused and D68's claim that this screen printed `1.2500h` does not hold there — that defect was in the pendency lists and internal work, which is where the literal `h` was concatenated.

## Test coverage

The renderer itself is well covered: the non-whole-minute cases (`1.8750`, `0.3750`, the 9-second floor, both negatives), a test that a whole-minute value emits no `0s` tail, a decided outcome for the sub-second last resort, `/preview` twins with the raw strings beside them, and the exact case the user reported (`1.25h` at a 1.5 multiplier reading `1h 52min 30s`). The client-facing `assert row["equivalent_hours_display"]` was strengthened into an exact string rather than left as the truthiness check the conventions document calls a false green.

Not tested: any of the six new `_display` fields; the consolidation payload shape after the change, whose only tests are the three failures above; and anything on the web side, because this fork has no JS test runner — the responsive change is guarded only by `tsc` and `oxlint`, neither of which can see a breakpoint. That is why the viewport-versus-container mismatch went unnoticed. With no browser in the sandbox, the cheapest substitute is a written manual matrix (390px, 768px, 1024px, 1440px × side-peek / modal / full-screen) run once against a real build after the push.

## Deliberately left alone

`issues/issue-detail/root.tsx` keeps `px-9` at every width, so the full-page work item — not the peek — still spends 72px of a 390px screen on padding. The findings argue it is core Plane geometry affecting title, description and activity feed alike, which is a defensible scope line, but it means the page the user reaches from a notification is still untouched on a phone. `modal` peek mode is `size-5/6` at every width, so it is 83% of a 390px screen with no mobile-specific sizing and only the new `px-4` helping it.

No decision entry covers the responsive half. D68 records the hour rendering only, so the reasoning the next person needs — mobile-first prefixing, `sm` for rows and `md` for grids, and the load-bearing `!w-[400px]` bang — lives in code comments and task state rather than in `DECISOES.md`.
